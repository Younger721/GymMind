# AI 中心自动 RAG 与工具编排设计

## 背景

AI 中心目前把 `knowledge_search` 作为用户可手动切换的 RAG 开关，同时将门店运营、课程、训练记录等能力交给 LLM 通过 tool calling 自主判断。两套能力的入口和展示方式不一致，用户关闭 RAG 后容易误以为所有业务数据工具也被关闭；在支持原生工具调用的模型路径中，传统 RAG 插件还可能被跳过。

## 目标

- 保留知识库检索作为回答依据，不让用户承担 RAG 开关决策。
- 让 LLM 继续自主决定是否调用受权限保护的业务工具。
- 用户可见界面不再显示“RAG 已启用/未启用”切换按钮。
- 回答过程仍展示知识库检索和业务工具的执行明细及引用来源。
- 没有检索结果时不伪造依据；模型异常或检索异常保持现有降级行为。

## 方案

采用“自动检索 + 自主工具调用”方案：

1. 每次知识咨询先执行当前租户权限范围内的知识库检索，将结果作为上下文传给模型。
2. 模型支持 tool calling 时，再把符合当前角色权限的业务能力作为工具交给模型，由模型决定是否调用。
3. 模型不支持 tool calling 时，保留现有插件/规则兜底路径。
4. `knowledge_search` 继续作为后端能力和平台/租户配置项存在，用于权限、可用性和执行过程，不再作为会话级用户开关。
5. 前端将状态文案改为“知识库与业务数据按权限自动匹配”，回答标签改为“知识库依据”或“业务数据回答”，不展示手动 RAG 状态。

## 数据流

```text
用户问题
  -> 权限范围内知识库检索
  -> 生成知识上下文与引用
  -> LLM tool calling（可选，业务数据工具）
  -> LLM 结合上下文和工具结果生成回答
  -> 返回回答、引用、执行过程
```

知识库检索失败时记录失败过程并按现有错误策略处理；业务工具失败时保留工具错误上下文，由模型明确说明数据不可用，不推测缺失数据。

## 代码边界

- `DefaultAiHarnessService`：统一自动执行知识检索，再执行原生工具编排；移除对会话级 `knowledge_search` 开关的依赖。
- `AssistantView.vue`：删除 RAG 切换按钮、相关状态和会话插件切换逻辑；保留执行过程、引用来源和工具状态展示。
- `KnowledgeSearchHarnessPlugin`：保留作为后端检索能力和非原生工具调用路径的兼容实现。
- `AiToolOrchestrator`：继续只暴露权限允许的只读业务工具；知识库上下文由编排服务统一注入。

## 错误与兼容

- 未找到知识片段时，不显示虚假的引用；纯业务问题仍可由工具回答。
- 旧会话请求中携带 `knowledge_search` 插件 ID 时，后端忽略该会话级开关并按自动策略执行。
- 旧租户/平台配置中的 `knowledge_search` 保留，继续作为能力可用性和权限配置，不删除数据库值。
- 不保存 prompt、完整回答或 API 密钥。

## 验收与测试

- 前端不再渲染 RAG 开关，发送请求不再依赖会话级 RAG 状态。
- 启用知识库时，每次咨询都能看到检索执行过程和真实引用；无结果时不伪造来源。
- 门店运营问题仍由模型自主调用运营工具，并且租户权限隔离不变。
- 原生 tool calling 与非原生插件路径都能生成回答。
- 检索失败、工具失败、模型未配置时保持可理解的降级提示。
- 后端目标测试、前端 `npm run build` 和相关权限测试通过。
