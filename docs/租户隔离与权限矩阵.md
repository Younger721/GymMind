# GymMind 租户隔离与权限矩阵

## 隔离方案

GymMind 采用“共享数据库、共享表、`tenant_id` 区分”的 SaaS 隔离方案。业务请求的租户由 JWT 认证上下文解析，客户端传入的 `tenantId` 只能用于一致性校验，不能切换租户。

普通租户请求必须具有租户上下文；缺失上下文返回 403。平台管理员默认处于平台上下文，只能访问平台专用接口，不能因为请求头或查询参数自动进入某个租户。

## 查询约束

- 根业务实体使用 `findByTenantIdAndId`、`findAllByTenantId...` 等租户前缀仓储方法。
- Agent、知识库、AI 用量、审计查询必须带租户条件；平台全局查询只能由平台专用统计/审计接口执行。
- `WorkoutPlanItem`、`WorkoutSet` 等子表不单独信任请求中的 ID，必须先以租户条件解析父记录，再访问子记录。
- RAG 索引、调用日志和缓存键均包含 `tenantId`，检索结果不得跨租户混合。
- `member_profile` 保存会员全局资料，`member_tenant` 保存会员在每个健身房的独立状态；所有会员列表、更新和关系校验都必须使用 `(tenant_id, member_id)`。
- `coach_member_assignment` 是同租户多对多关系，状态为 `PENDING`、`ACTIVE`、`REJECTED` 或 `ENDED`。会员发起申请，教练只能处理自己收到的申请。

## 演示验证

1. A 租户创建会员、知识文档和 Agent。
2. 使用 B 租户账号请求相同资源 ID，返回 404 或 403，列表不出现 A 的数据。
3. 平台管理员通过平台统计接口查看聚合数量，但访问普通租户详情接口仍被拒绝。

## 会员教练申请流程

1. 会员在当前健身房选择教练，调用 `POST /api/v1/coach-relations/requests`，服务端从 JWT 取得会员身份和租户，不接受客户端伪造的 `tenantId`。
2. 教练通过待处理列表查看 `PENDING` 申请，调用接受或拒绝接口。
3. 只有 `ACTIVE` 关系允许教练读取会员训练数据；会员可取消待处理申请，任一方可结束已建立关系。
